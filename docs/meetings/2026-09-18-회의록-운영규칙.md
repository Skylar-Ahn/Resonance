# Resonance Discussion Note

> **Date:** 2026-09-18  
> **Topic:** 회의록 작성 및 GitHub 아카이빙 운영 규칙  
> **Area:** Automation / Documentation  
> **Status:** Decided  
> **Related:** `docs/meetings/README.md`, `docs/meetings/TEMPLATE.md`, `docs/00_README.md`

## 1. Context

Resonance의 기획·디자인·기술 논의가 여러 대화에 분산되면서, 결정의 배경과 미확정 사항을 짧고 일관된 형식으로 보존할 필요가 생겼다. 대화를 그대로 요약하는 일반 회의록 대신, 결정과 판단 근거를 중심으로 한 Discussion Note를 GitHub에 축적하기로 했다.

## 2. Key Discussion

| 구분 | 핵심 내용 |
| --- | --- |
| 고민한 문제 | 대화에서 나온 제안·피드백·결정·미결 사항을 다시 찾기 쉽고 구현 문서와 혼동되지 않게 보존하는 방법 |
| User 제안 | `#회의록`을 입력하면 현재 대화를 간결한 회의록으로 정리해 Resonance 저장소의 `docs/meetings/`에 올리는 방식 제안 |
| ChatGPT 제안 | Decision-oriented Discussion Note 형식, `Decided / Tentative / Open Questions` 분리, GitHub 템플릿을 단일 원본으로 사용하는 운영 방식 제안 |
| 상호 피드백 | 사용자는 핵심만 간결하게 남기되 필요할 때 표·다이어그램·이미지를 허용했다. 이에 회의록과 canonical specification을 분리하고, 문서 동시 반영은 별도 트리거로 구분했다. |
| 제약·전제 | 사용자가 확정하지 않은 내용을 결정으로 기록하지 않으며, 반복 목업 수정·단순 질의응답·잡담은 판단 복원에 필요하지 않으면 제외한다. |

## 3. Options Considered

### Option A — 프로젝트 소스와 GitHub에 템플릿 중복 저장

- 핵심: ChatGPT 프로젝트 소스와 저장소에 같은 템플릿을 각각 둔다.
- 장점: 어느 환경에서도 템플릿을 바로 참조할 수 있다.
- 문제점: 한쪽만 수정될 경우 형식과 규칙이 서로 달라질 수 있다.

### Option B — GitHub 템플릿을 단일 원본으로 사용

- 핵심: `docs/meetings/README.md`와 `docs/meetings/TEMPLATE.md`를 canonical source로 삼고 프로젝트 지침은 이를 참조한다.
- 장점: 규칙과 템플릿의 버전이 한곳에서 관리된다.
- 문제점: 회의록 작성 전에 GitHub 파일을 확인해야 한다.

## 4. Decisions

### Decided

- **D-01. GitHub의 회의록 규칙과 템플릿을 단일 원본으로 사용한다.**
  - 이유: 프로젝트 소스와 저장소 사이의 템플릿 불일치를 방지하기 위해서다.
  - 영향 범위: ChatGPT 프로젝트 지침, 향후 모든 Discussion Note 작성.

- **D-02. 사용자가 `#회의록`을 입력하면 현재 논의를 회의록으로 작성한다.**
  - 이유: 별도 장문의 프롬프트 없이 일관된 아카이빙 동작을 실행하기 위해서다.
  - 영향 범위: 현재 대화 전체 또는 같은 대화에서 직전 `#회의록` 이후의 새 논의.

- **D-03. 회의록은 `docs/meetings/YYYY-MM-DD-회의주제.md` 형식으로 저장한다.**
  - 이유: 날짜와 주제로 쉽게 검색하고, 독립 논점을 파일 단위로 분리하기 위해서다.
  - 영향 범위: 파일 경로와 이름, GitHub 기본 브랜치 반영.

- **D-04. 회의록은 논의 이력이며 canonical specification을 대체하지 않는다.**
  - 이유: 과거 대안과 현재 유효한 제품 기준이 섞이는 것을 막기 위해서다.
  - 영향 범위: IA, User Flow, Product Spec, 디자인·데이터·추천 문서, Decision Log.

- **D-05. `#회의록`만으로 기존 canonical 문서를 자동 수정하지 않는다.**
  - 이유: 회의록 작성만으로 문서 변경 범위가 불필요하게 커지는 것을 막기 위해서다.
  - 영향 범위: 확정 결정은 회의록의 Follow-ups에 반영 대상을 기록한다.

- **D-06. `#회의록+문서반영` 요청 시에만 확정 결정과 영향 문서를 함께 검토·갱신한다.**
  - 이유: 논의 이력 저장과 현재 명세 갱신을 사용자가 명시적으로 구분할 수 있게 하기 위해서다.
  - 영향 범위: 관련 canonical 문서와 Decision Log.

- **D-07. 독립적인 논점은 하나의 긴 회의록에 합치지 않고 주제별 파일로 분리한다.**
  - 이유: 나중에 개별 의사결정의 맥락을 빠르게 찾기 위해서다.
  - 영향 범위: 회의록 파일 단위와 제목.
