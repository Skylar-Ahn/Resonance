# Resonance Discussion Note

> **Date:** 2026-09-18  
> **Topic:** 사전 감상 아티클 콘텐츠 원칙과 출처 정책  
> **Area:** Product / Data  
> **Status:** Partially Decided  
> **Related:** Articles IA, Article Detail, 향후 Editorial Spec / Source Policy

## 1. Context

Resonance의 사전 감상용 아티클 생성 AI를 설계하기 전에, 기술 아키텍처보다 먼저 아티클에 어떤 정보가 들어가야 하는지와 어떤 자료를 신뢰·사용할 수 있는지를 정리했다. 목표는 음악학 백과사전식 정보 축적이 아니라, 사용자가 공연 전에 필요한 맥락을 익혀 실제 감상 경험을 더 깊게 만드는 것이다. 또한 AI가 프로그램 기획 의도나 연주자의 해석을 근거 없이 만들어내지 않도록 콘텐츠 생성 경계를 함께 논의했다.

## 2. Key Discussion

| 구분 | 핵심 내용 |
| --- | --- |
| 고민한 문제 | 작곡가·음악사·작품·연주자 정보를 어느 깊이까지 다룰지, 공연별 특수한 감상 포인트를 어떻게 반영할지, 신뢰 가능한 자료와 재사용 가능한 자료를 어떻게 구분할지 검토했다. |
| User 제안 | 작곡가 설명, 음악사적 배경, 작품의 제작·사회문화적 맥락과 악장별 감상 포인트, 연주자 소개와 예술관/해석을 기본 후보로 제안했다. 연주자 직접 발언을 찾지 못하면 해당 항목 자체를 삭제하는 방식을 선호했다. |
| ChatGPT 제안 | 작품 탄생·개정 이력, Listening Map, 음향·편성, 복수의 해석, 프로그램 전체의 관계, 관객 참여·특수 악기 등 공연별 Special Note를 추가했다. 자료가 없거나 특별한 점이 없으면 섹션을 생성하지 않는 evidence-driven modular article 원칙을 제안했다. |
| 상호 피드백 | 작곡가 전체 생애를 고정적으로 깊게 다루는 방식은 여러 작곡가가 포함된 공연에서 과도하다는 데 의견이 모였다. 프로그램 자체의 테마가 명시적이지 않은 공연이 많으므로 기획 의도를 AI가 추론해 서사화하지 않는 방향으로 조정했다. |
| 제약·전제 | 신뢰성, 무료 접근 가능성, 재사용 권리는 서로 다른 문제다. 공개 웹페이지나 프로그램 노트가 신뢰할 만하더라도 자동 수집·재가공 권한이 자동으로 생기는 것은 아니다. |

## 3. Options Considered

### Option A — 고정형 아티클 템플릿

- 핵심: 모든 공연에 작곡가, 시대, 작품, 연주자, 해석 섹션을 동일하게 생성한다.
- 장점: 생성 규칙과 화면 구조가 단순하다.
- 문제점: 자료가 없는 항목을 억지로 채우거나, 여러 작품·작곡가가 있는 공연에서 과도하게 길어질 수 있다.

### Option B — Evidence-driven Modular Article

- 핵심: 공통 핵심 정보는 유지하되 Program Story, Artist Perspective, Special Note 등은 근거와 필요가 있을 때만 삽입한다.
- 장점: 공연마다 필요한 정보 밀도를 조절할 수 있고 AI의 과잉해석을 줄인다.
- 문제점: 모듈 선택 기준과 검수 정책을 별도로 정의해야 한다.

## 4. Decisions

### Decided

- **D-01. 사전 감상 아티클의 목적은 공연 전에 필요한 배경지식을 제공해 실제 청취 경험을 강화하는 것이다.**
  - 이유: 제품의 Articles 영역은 음악학 백과사전이 아니라 공연 경험의 준비 단계에 해당한다.
  - 영향 범위: Articles 콘텐츠 정책, AI 생성 목표, Editorial Spec.

- **D-02. 작곡가 정보는 전체 생애 요약이 아니라 해당 작품을 이해하는 데 필요한 맥락만 선택한다.**
  - 이유: 여러 작곡가·작품이 포함된 공연에서 정보 과잉과 반복을 막기 위해서다.
  - 영향 범위: Work Note 및 Concert Guide 콘텐츠 구성.

- **D-03. 연주자의 해석·예술관은 연주자 본인의 직접 발언 또는 명확한 1차 근거가 있을 때만 사용하고, 자료가 없으면 섹션 자체를 렌더링하지 않는다.**
  - 이유: 평론가의 평가와 연주자 본인의 의도를 혼동하지 않기 위해서다.
  - 영향 범위: Artist Perspective 생성·표시 규칙.

- **D-04. 프로그램의 기획 의도는 확인 가능한 근거가 있을 때만 '의도'로 서술한다.**
  - 이유: 실제 공연 프로그램이 항상 하나의 깊은 테마를 전제로 기획되는 것은 아니며, AI가 사후적으로 의미를 만들어내는 것을 방지해야 한다.
  - 영향 범위: Program Story, 프로그램 관계 설명.

- **D-05. 공연마다 존재할 수 있는 관객 참여, 특수 악기, 무대 연출, 특정 청취 포인트 등은 조건부 Special Note로 다룬다.**
  - 이유: 공연별 예외적 감상 정보는 가치가 크지만 모든 공연에 강제할 수 없다.
  - 영향 범위: Concert Guide 모듈 구성.

### Tentative

- **T-01. 출처는 신뢰성과 이용권한을 분리해 Green / Yellow / Red 등급으로 관리하는 방향을 채택한다.**
  - 추가 검증 또는 결정이 필요한 내용: 상업화 가능성을 전제로 한 각 라이선스별 허용 범위와 자동 수집 정책.

- **T-02. Wikidata, MusicBrainz Core, RISM, Europeana metadata, OpenAlex 등 구조화·오픈 데이터를 기본 사실 검증층의 주요 후보로 사용한다.**
  - 추가 검증 또는 결정이 필요한 내용: 실제 허용 라이선스, attribution 요구사항, API/대량 사용 조건을 소스별로 확정해야 한다.

- **T-03. 학술 논문, 전문기관, 오케스트라·공연장 프로그램 노트, 공식 인터뷰 등은 검증·근거 자료로 사용하되 원문 표현의 대규모 복제나 단순 재서술을 기본 생성 전략으로 사용하지 않는다.**
  - 추가 검증 또는 결정이 필요한 내용: 인용 길이, 저장 방식, 사이트별 이용약관 검토 기준.

## 5. Open Questions

- **Q-01.** AI가 최종 아티클에 사용할 수 있는 출처 allowlist와 차단할 source 유형을 어떻게 정의할 것인가?

- **Q-03.** 각 claim과 출처의 연결을 어느 단위까지 저장·노출할 것인가?
